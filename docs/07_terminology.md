# 用語と説明のガイド

後から読んでも、対象、操作、比較条件、結果を理解できる記録を残す。
共通ルールの正本は [AGENTS.md](../AGENTS.md#用語と説明)。各用途のスキルにもこのルールが適用される。

## 書き方

1. 普通の操作は具体的な日本語で書く。短く呼ぶためだけの新しい用語を作らない。
2. 定着した専門用語は使ってよい。初出で意味を説明し、繰り返し使うものは問題設定文書の「用語と名称」に登録する。
3. コンペ公式の名称やコードの識別子はそのまま示し、説明を添える。外部資料の独自名は出典の呼称だと明示する。
4. 案件固有の名称は必要性がある場合だけ定義する。対象や手順が曖昧なまま、用語集に載せて正当化しない。
5. 用語集はセッションをまたいで引き継ぐ。読み手への短い説明は、その都度の報告にも添える。

## 言い換えの例

以下の左列は曖昧な書き方の例であり、禁止語の一覧ではない。

| 分かりにくい記述 | 具体的な記述 |
| --- | --- |
| OOF 台帳を整備する | 学習に使っていない各行の予測（OOF: Out-of-fold prediction）を、行 ID と分割番号付きで保存する |
| CV 護衛を入れる | 同じ顧客のデータが学習用と検証用に分かれないよう、顧客 ID で分割する |
| 昇格ゲートを通す | 同じ分割で現行モデルより RMSE が低く、推論時間が 1 秒以下なら採用する（数値は例） |
| signal pack を追加する | 直近 7 日間の購入回数と購入金額の合計を特徴量に追加する |
| exp012 は強い | exp012 は同じ 5 分割で exp011 より平均 RMSE が 0.02 低かった。分割ごとの結果と実行時間も確認する（数値は例） |

「改善」「安全」「強い」だけで結論にしない。指標の定義と比較条件は評価文書に、実測値は実験記録に残す。

## 用語の記録先

`aidlc-docs/inception/problem-overview.md` の「用語と名称」を使う。
その内容は生成 HTML の Problem Overview にも表示される。

- 種別: 一般用語 / 公式名称 / 案件固有 / コード識別子。
- 意味・範囲: 一文の定義と、対象になるデータや処理。似た名称との違いが必要なら補足する。
- 具体例・参照: 列名、ファイル、設定キー、実験 ID、または定義が載っている出典。
- 旧名: 以前の呼び名があれば残す。変更理由と日付も記録する。

全単語の登録は不要。初出で説明すれば足りる単発の用語と、繰り返し使う名称を区別する。
派生案件では、その案件に必要な定義を記入する。

## 報告前の確認

- 前の会話を知らなくても、何のデータ・処理・結果か分かる。
- 略語と案件固有の名称に説明があり、用語集と意味が一致する。
- 実験の ID、変更内容、比較相手、評価条件が分かる。
- 実測、資料の報告、仮説を読み分けられる。

言い回しは agent が修正する。名称の意味や評価条件が確定できないときは、質問を具体化して確認する。
